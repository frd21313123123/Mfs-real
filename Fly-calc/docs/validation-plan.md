## Протокол проверки внутри симуляторов

Выполнить **отдельно** на MSFS 2020 и 2024. Записать версии симулятора, A32NX SHA, hash patch/build, Windows, локального сервиса и nav snapshots. Включить `FBW_TYPECHECK=1`, завершить upstream проверки. Установить собственную сборку по инструкции FBW; сохранить штатную версию вне Community.

1. Холодный запуск самолёта: открыть flyPad, проверить питание и исходные функции, кнопку FC и страницу Fly-calc.
2. UUEE → ULLI, FBW: ввод клавиатурой/мышью, swap, неизвестный ICAO и повторяющийся аэропорт. Ошибки должны отображаться и не ломать штатные страницы.
3. Получить test probe по XHR к localhost:8147. Все расчётные поля пусты; название самолёта и аэропортов соответствует справочнику.
4. В Windows загрузить разрешённый многостраничный PDF для вылета, назначения и третьего ICAO. В flyPad открыть список, переключить страницы, проверить чёткость, прокрутку и соответствие ICAO. Проверить тестовый PDF. Никакой рассчитанный запасной не появляется сам собой.
5. Остановить сервис при открытой вкладке и повторить запрос: получить понятную ошибку. Перезапустить сервис и нажать «Переподключить»: восстановить ввод/документы без перезапуска самолёта. Проверить незавершённую загрузку изображения.
6. Проверить переходы на штатные страницы, закрытие EFB/смену питания/возврат: нет утечек обработчиков, конфликтов CSS, блокировки toolbar и полос прокрутки вне экрана.
7. Восстановить штатный A32NX, повторить запуск и основные функции. Сохранить журнал, скриншоты и результат каждой проверки. Любой неподтверждённый пункт остаётся pending.

Fenix проходит аналогичный протокол только после подтверждения расширяемости. Браузерное открытие `/fenix` сейчас проверяет companion, а не этот native protocol.

## Протокол допуска навигационной базы

У каждого source snapshot сохранить разрешение использования, URL/hash, реальную effective date/цикл, schema/version и полный перечень записей. Для полноты нужен заранее определённый эталон/перечень ожидаемых сущностей; семь примеров не заменяют знаменатель.

Проверить по всему набору уникальность scoped identifiers, конфликтующие координаты, runway parent links, обрезанные/некорректные записи, направления и диапазоны высот, airspace/equipment conditions. Для процедур декодировать primary/continuation records, leg types, runway/enroute/common transitions, ограничения скорости/высот и missed approach. На известных тестовых случаях сравнить последовательности с официальными схемами. Записи с неизвестной семантикой карантинировать, а не достраивать эвристикой.

Межцикловые наборы должны иметь явный compatibility policy. Неподтверждённые RAD/NOTAM/закрытия показывать в каждом будущем OFP. До успешной проверки мирового источника gate остаётся закрыт.

## Калибровка характеристик каждого аддона

Версия профиля фиксирует точную версию аддона, симулятора, двигатель, режимы CI/скоростей, единицы топлива, payload/ZFW/CG и настройки realism. Новая версия flight model требует новой проверки. Fenix/PMDG/ToLiss/Zibo нельзя допустить по результатам FBW.

Сначала собрать **калибровочные** данные: установившиеся cruise точки по высоте/массе/ISA, climb/descent по согласованному скоростному профилю, holding и отдельно taxi/APU. Если разрешённых таблиц нет, использовать собственные измерения в законно установленном аддоне; телеметрию и право дальнейшего распространения проверять отдельно. Исходные измерения хранить, ошибочные/незавершённые полёты отмечать.

Отдельные **проверочные полёты** не использовать для подгонки параметров:

| Семейство | Дальности, морские мили | Массы | Ветер |
|---|---|---|---|
| Fenix/FBW/PMDG 738/Zibo/ToLiss | примерно 250 / 750 / 1 500 | лёгкая / средняя / тяжёлая в пределах конкретного аддона | нулевой / встречный / попутный |
| PMDG 777-300ER | примерно 500 / 2 500 / 6 000 | лёгкая / средняя / тяжёлая допустимая | нулевой / встречный / попутный |

План минимум 9 независимых holdout-полётов на профиль: распределить комбинации так, чтобы все три диапазона расстояния, массы и ветра были представлены. Добавить сложные descent/holding кейсы отдельно. Конкретные маршруты выбирать после подтверждения данных; указанные дальности не являются уже выполненными полётами. MSFS 2020/2024 для FBW проверять отдельно; двигатель и версия X-Plane тоже разделяют наборы.

В reference и расчёте одинаковы маршрут/процедуры, эшелоны, массы, температура/ISA, заданный постоянный ветер, CI/Mach и ограничения. Сначала фиксированная погода; live weather и ATC deviations — отдельная проверка. Не смешивать ground delay с airborne временем.

- **Trip time**: от takeoff до touchdown в симуляторе; planned/reference используют ту же границу.
- **Trip fuel**: разность топлива takeoff–touchdown. Утечки/рефюэлинг/изменение payload во время полёта исключают запись.
- **Block fuel/time**: отдельные taxi/APU, ground time, alternate/missed approach, contingency/final reserve; не сравнивать block с trip.
- **Ошибка**: `100 × abs(planned − observed) / observed`, отдельно для fuel и time; observed должен быть больше нуля.

Допуск — **не более 5% для обоих показателей на каждом holdout-полёте**, не среднее, скрывающее отдельные ошибки. Указать область, в которой профиль прошёл проверку; за её пределами показывать unvalidated. Alternate/hold/reserves требуют собственных сценариев. СимBrief может быть вторым сравнением при совпавших условиях, но измеренный аддон остаётся reference; чужой результат не заменяет свой расчётный движок.

Сохранять сырую телеметрию, версии, input JSON, хэши источников, predicted/observed, ошибки и pass/fail. Сейчас таких результатов нет; обещание 5% не даётся.
